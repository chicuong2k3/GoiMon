# ADR-005: Sync Event Schema and Queue Contract

**Status**: Accepted
**Date**: 2026-03-07
**Context**: GoiMon.Staff (Blazor WASM PWA) is an offline-first app that must reliably persist local actions and synchronize them to the server when connectivity is available. A deterministic, versioned event envelope and a well-defined queue contract are required so that replay, deduplication, ordering, and error-handling can be implemented consistently across clients and server.

## Decision
Define a language- and transport-agnostic event envelope and explicit queue-state contract. Use client-generated identifiers and server-side deduplication. Provide a clear retry policy and dead-letter behavior.

## Event Envelope (Base Contract)
All sync messages MUST conform to this envelope.

```json
{
  "eventId": "uuid-v4",           // unique identifier for this event instance
  "eventType": "OrderCreated.v1", // namespaced event type with version
  "schemaVersion": "1.0",        // envelope schema version
  "aggregateType": "Order",       // aggregate name
  "aggregateId": "uuid-v4",      // aggregate identifier (client-generated for new aggregates)
  "aggregateVersion": 1,           // monotonic version number for the aggregate (client-provided where possible)
  "tenantId": "tenant-123",      // tenant/store id
  "actor": {                       // who/what produced the event
    "userId": "user-uuid",       // staff id or system
    "deviceId": "device-uuid"
  },
  "timestamp": "2026-03-07T12:00:00Z", // ISO-8601 UTC when event was created locally
  "idempotencyKey": "uuid-v4",  // idempotency key for non-entity operations
  "correlationId": "trace-id",  // optional trace id for observability
  "causationId": "eventId-of-cause", // optional causal link
  "payload": { /* typed event payload */ },
  "metadata": { "key": "value" } // optional vendor-specific metadata
}
```

Field requirements and notes:
- `eventId` (required): UUID v4 generated by client.
- `eventType` (required): String using pattern `<Aggregate><Action>.v<Major>` (e.g., `OrderCreated.v1`). Minor schema changes should bump minor version in `schemaVersion` or in `eventType` semantics where necessary.
- `schemaVersion` (required): Envelope schema version. Increment on breaking changes to envelope.
- `aggregateVersion` (optional but recommended): If present, server should reject applying an event with `aggregateVersion` <= stored version to avoid stale writes.
- `idempotencyKey` (required for operations that may be retried and are not pure entity upserts): server must deduplicate on this key for at least 24 hours (configurable TTL).
- `tenantId` (required): All events must include tenant/store id in multi-tenant SaaS.
- `payload` (required): JSON object validated against event-type-specific schema.

## Event Type Schema Versioning
- Version event payloads by including a `v<major>` suffix in `eventType` (e.g., `OrderConfirmed.v2`).
- Non-breaking changes: add optional fields (server must ignore unknown fields).
- Breaking changes: create new event type with incremented major version (consumer adapts explicitly).

## Queue States and State Machine
Client local queue entries MUST track the following states:
- `Pending` — created locally, not yet sent
- `Processing` — in-flight to server
- `Acked` — server acknowledged successful processing
- `Failed` — permanent business-level failure (user action required)
- `DeadLetter` — exceeded retry attempts; admin review required

State transitions:
- Pending -> Processing (on send)
- Processing -> Acked (on 2xx/app-level success)
- Processing -> Pending (on transient network failure, after applying backoff)
- Processing -> Failed (on business rejection e.g., validation or constraint violation)
- Failed -> DeadLetter (after manual fail threshold or explicit admin decision)

## Retry Policy
- Retries use exponential backoff with full jitter; base delay = 1s, max delay = 60s.
- MaxRetryAttempts = 5 by default (configurable per tenant).
- On transient network errors, client should set entry back to `Pending` and schedule retry.
- On 4xx business errors where client can fix data (e.g., out of stock), mark `Failed` and surface to user.

## Idempotency and Deduplication
- Server MUST deduplicate events by `eventId` first. If `eventId` is missing, fall back to `idempotencyKey` where applicable.
- Server stores processed `eventId` + result for TTL (minimum 24h) to allow safe retry.
- For commands that create aggregates, client-generated `aggregateId` prevents duplicate creation when retried.

## Ordering Guarantees
- Ordering is guaranteed only per-aggregate when clients provide `aggregateVersion` or monotonic sequence numbers. Server must apply events for an aggregate in `aggregateVersion` order or return a retryable error when out-of-order.
- Cross-aggregate ordering is not guaranteed.

## Schema Registry / Validation
- The server should expose an endpoint (or storage) listing `eventType` → JSON schema (for validation and contract tests).
- Clients and CI should run contract tests against these schemas.

## Contract Tests
- Contract test: Validate required envelope fields and `payload` shape for each `eventType`.
- Replay test: Replaying same event twice must be idempotent; server response should reflect 'already processed' and not create duplicates.
- Ordering test: Apply events with versions 1..N and verify server state matches expected final state.

## Security & Integrity
- Events sent over TLS only.
- Optionally sign events with tenant scoped HMAC for additional server-side integrity check.
- Do not include secrets or provider keys in payloads.

## Monitoring & Observability
- Instrument: queue depth, queue processing latency, retry counts, dead-letter counts, per-tenant failure rates.
- Expose metrics to dashboard and alerts when dead-letter rate crosses threshold.

## Consequences
- Deterministic replay and robust deduplication reduce reconciliation workload.
- Slightly higher implementation cost (schema registry, de-dupe store), but improves long-term reliability.

## Acceptance Criteria
- Event envelope documented and sample payloads provided.
- Queue state machine and retry policy documented with defaults.
- Contract tests created (specification) to validate schema and idempotency.
