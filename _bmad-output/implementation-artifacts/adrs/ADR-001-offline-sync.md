# ADR-001: Offline Sync & Idempotency Strategy

**Status**: Accepted
**Date**: 2026-03-07
**Context**: GoiMon.Staff (Blazor WASM PWA) needs to operate reliably in intermittent connectivity (Vietnam market). Orders must be created locally first.

## Decisions

### 1. Local-First Write Model
-   **Principle**: All user actions (Place Order, Edit Order) write immediately to the local **SQLite-Wasm** database.
-   **Technology**: **Bit.Besql** library (EF Core + SQLite in browser), **EasyAppDev.Blazor.Store** (UI state management), **Blazored.LocalStorage** (token/config).
    -   **Bit.Besql**: Used for domain data (Orders, Products, Inventory) with EF Core/SQLite.
    -   **EasyAppDev.Blazor.Store**: Used for UI state management and synchronization between database and UI.
    -   **Blazored.LocalStorage**: Used for lightweight, fast storage (tokens, UI flags).
-   **Architecture**:
    -   UI -> Blazor Store (State) -> SQLite (Bit.Besql + EF Core) -> Sync Queue (Background).
    -   The UI reflects the *local state* instantly, without waiting for the server.

### 2. Synchronization Queue (Outbox Pattern)
-   **Mechanism**: A dedicated `SyncQueue` table in SQLite.
-   **Schema**:
    -   `Id`: UUID (Primary Key)
    -   `Operation`: Enum (CreateOrder, UpdateOrderStatus, SyncInventory...)
    -   `Payload`: JSON (Serialized DTO)
    -   `CreatedAt`: Timestamp
    -   `Status`: Pending / Processing / Failed / Completed
    -   `RetryCount`: Int
-   **Process**:
    -   A background service (Blazor `PeriodicTimer` or `IHostedService`) polls the queue every X seconds (e.g., 5s) when online.
    -   It sends the payload to the GraphQL API.
    -   On success (200 OK), mark as Completed (and remove after T time).
    -   On failure (Network Error), retry with exponential backoff.
    -   On failure (Business Error - e.g., "Item out of stock"), mark as Failed and notify user to resolve manually.

### 3. Idempotency Strategy
-   **Problem**: Network flakes can cause duplicate requests (Client sends, Server processes, Response lost, Client retries).
-   **Solution**: **Client-Generated IDs (UUID v4)** for all entities.
    -   `OrderId` is generated by the Client, NOT the Database.
    -   Server checks `IF EXISTS (SELECT 1 FROM Orders WHERE Id = @Id)` before inserting.
    -   For non-entity actions (e.g., "Pay Order"), send an `IdempotencyKey` header (UUID) with the request. Server caches this key for 24h.

### 4. Conflict Resolution
-   **Strategy**: **Last-Write-Wins (LWW)** based on Server Timestamp for simple fields (Notes, Table Number).
-   **Exception**:
    -   **Order Status**: Finite State Machine (FSM) enforces valid transitions (Draft -> Confirmed -> Paid). Server rejects invalid transitions.
    -   **Inventory**: Delta updates (Decrement/Increment) preferred over absolute set. Or use "Optimistic Concurrency Control" (Version number) - if server version > client version, reject and ask user to refresh.

## Consequences
-   **Positive**: Zero-latency UI. Resilient to flakiness.
-   **Negative**: Complexity in error handling (What if local order is invalid on server?). UI must handle "Syncing..." and "Sync Error" states.
